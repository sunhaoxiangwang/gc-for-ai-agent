# Recipes

Complete, runnable configs for each stack are in [`examples/`](../examples/).
Every one of them is validated in CI by running `reap doctor` against it.

Try any of them without installing anything:

```sh
reap --config examples/rust.toml report
```

The sizes below are what you can reasonably expect on a working developer
machine. They vary enormously with how many projects you have checked out and
how long ago you last cleaned up, so treat them as orders of magnitude rather
than predictions. Run `reap report` for the real number on your machine.

## Rust

[examples/rust.toml](../examples/rust.toml)

| What | Tier | Typical size |
| --- | --- | --- |
| `target/` per project | 0 | 500 MB to 5 GB each |
| `~/.cargo/registry/{cache,src}` | 2 | 1 to 5 GB total |

Usually the single biggest win on a Rust machine. A handful of active projects
comes to 10 to 40 GB of `target/` without anyone noticing.

The rule uses `require_sibling = "Cargo.toml"`, so a directory that merely
happens to be named `target` is never a candidate.

Prevention beats reclamation here:

```sh
export CARGO_TARGET_DIR="$HOME/.cache/cargo-target"
export RUSTC_WRAPPER=sccache
```

One shared build directory instead of one per project, and a compilation cache
shared across all of them. If you set these, the tier 0 rule will find much less
to do, which is the point.

## Node, npm and pnpm

[examples/node.toml](../examples/node.toml)

| What | Tier | Typical size |
| --- | --- | --- |
| `node_modules` per project | 1 | 200 MB to 1.5 GB each |
| `.next`, `.nuxt`, `.turbo`, `.parcel-cache` | 1 | 100 MB to 2 GB each |
| pnpm store | 2 | 2 to 10 GB |
| npm cache | 2 | 500 MB to 3 GB |

Twenty checked-out projects is comfortably 10 to 20 GB of `node_modules`. The
idle window is 14 days by default, because a reinstall costs minutes and
bandwidth rather than seconds.

`reap` never proposes a nested `node_modules` inside another one separately: the
walker does not descend into a directory it has already selected.

Prevention: pnpm keeps one content-addressed store across every project, which
is most of the reason to use it.

## Python, venvs and uv

[examples/python.toml](../examples/python.toml)

| What | Tier | Typical size |
| --- | --- | --- |
| `__pycache__` | 0 | a few MB each, hundreds of them |
| `.pytest_cache`, `.mypy_cache`, `.ruff_cache` | 0 | 10 to 200 MB each |
| `htmlcov` | 0 | 5 to 50 MB each |
| `.venv` per project | 1 | 200 MB to 3 GB each |
| uv cache | 2 | 1 to 10 GB |

The bytecode and tool caches are individually small and collectively a few
hundred megabytes. Virtual environments are the real weight, especially once
anything scientific is installed: a single environment with PyTorch in it is
several GB on its own.

The venv rule uses `require_ancestor = ".git"`, so an environment you keep
outside any checkout is left alone.

Prevention:

```sh
export PIP_CACHE_DIR="$HOME/.cache/pip"
export UV_CACHE_DIR="$HOME/.cache/uv"
```

## Xcode and iOS

[examples/macos-ios.toml](../examples/macos-ios.toml)

| What | Tier | Typical size |
| --- | --- | --- |
| `~/Library/Developer/Xcode/DerivedData/*` | 1 | 20 to 80 GB total |
| `~/Library/Developer/Xcode/iOS DeviceSupport/*` | 1 | 3 to 15 GB total |
| Unavailable simulator runtimes | 1 | 2 to 10 GB |
| `~/Library/Developer/CoreSimulator/Caches/*` | 2 | 1 to 5 GB |

This is the one to read if you do Apple platform work. DerivedData alone
routinely accounts for more than everything else on this page combined, and
nothing in the other recipes touches it.

Deliberately not included:

- `~/Library/Developer/Xcode/Archives`, which holds your shipped builds and
  their dSYMs. You need those to symbolicate a crash report from a release.
- `~/Library/Developer/CoreSimulator/Devices`, which holds simulator contents
  including any state you set up by hand.

If you want those gone, remove them deliberately, once, having looked at the
list. Not on a timer.

**Full Disk Access is required** for a scheduled job to read `~/Library`. See
[scheduling.md](scheduling.md).

## Go

Generated by `reap init --detect` when `go` is on your `PATH`, and included in
[examples/monorepo.toml](../examples/monorepo.toml).

| What | Tier | Typical size |
| --- | --- | --- |
| Go build cache | 0 | 1 to 10 GB |
| Module cache | 2 | 1 to 20 GB |

The build cache is a command rule (`go clean -cache`) rather than a path rule,
because Go manages its own layout and will do the right thing.

The module cache is read-only on disk by design, which makes it awkward to
remove directly; `go clean -modcache` is the supported way, and it is
deliberately not in the shipped examples because it is slow and re-downloading
is expensive. Add it yourself if you want it.

Prevention: `export GOCACHE="$HOME/.cache/go-build"`.

## Java and Gradle

[examples/monorepo.toml](../examples/monorepo.toml)

| What | Tier | Typical size |
| --- | --- | --- |
| `~/.gradle/caches/*` | 2 | 2 to 20 GB |
| `build/` per module | 1 | 50 MB to 1 GB each |

Gradle's caches grow steadily and are never pruned on their own. In a multi-module
project the per-module `build/` directories add up faster than the cache does.

Prevention: `export GRADLE_USER_HOME="$HOME/.gradle"` keeps it in one place if
anything on your machine has been persuaded to put it elsewhere.

## Docker

[examples/docker.toml](../examples/docker.toml)

| What | Tier | Typical size |
| --- | --- | --- |
| Dangling images | 1 | 2 to 20 GB |
| Stopped containers | 1 | small, but they hold image layers |
| Build cache | 2 | 5 to 50 GB |

Everything here is a command rule. Docker's storage is the daemon's, and
removing files underneath it corrupts it.

Deliberately not included: `docker volume prune` and `docker system prune
--volumes`. Volumes hold data, not caches.

On a machine that builds images regularly the build cache is often the single
largest item on the disk, larger than any language's artifacts.

## Headless browsers

Included by `init --detect` when it finds a Playwright or Puppeteer cache.

| What | Tier | Typical size |
| --- | --- | --- |
| Playwright browsers | 1 | 500 MB to 2 GB per version |
| Puppeteer Chromium | 1 | 300 MB to 1 GB per version |

The important thing here is prevention, not reclamation:

```sh
export PLAYWRIGHT_BROWSERS_PATH="$HOME/.cache/ms-playwright"
export PUPPETEER_CACHE_DIR="$HOME/.cache/puppeteer"
```

Without these, each project downloads its own copy of a browser, and a machine
that runs browser tests across several projects carries the same Chromium
five times over.

## Monorepos

[examples/monorepo.toml](../examples/monorepo.toml)

One repository, many packages, many languages. The problem is not finding
artifacts; it is walking a very wide tree quickly.

Two things make this config different:

- **Tight depth caps.** Rules that only ever match near the top say so with
  their own `max_depth`, which makes the walk much cheaper than the root's cap
  would.
- **The git-ignore guard does most of the work.** The whole repository is one
  work tree, so if your `.gitignore` is accurate, `reap` cannot touch anything
  you wrote.

Expect 20 to 60 GB on a monorepo that has been built a few different ways.

## Machines running unattended jobs

[examples/agent-workspaces.toml](../examples/agent-workspaces.toml)

CI runners, build farms, and machines running coding agents. Every job checks
out a repository, builds it, and often dies before cleaning up.

| What | Tier | Typical size |
| --- | --- | --- |
| Orphaned workspaces | 0 | 500 MB to 5 GB each |
| Orphaned session temp directories | 0 | 100 MB to 2 GB each |
| Per-workspace `node_modules`, `target` | 0 to 1 | as above, multiplied by concurrency |

The three-part integration (heartbeats, `gc-session` on exit, and a timer that
catches the rest) is described in the README and specified in
[configuration.md](configuration.md).

The rules here use `orphaned_only = true`, which demands positive evidence that
no live session owns a directory rather than assuming it. On these machines the
cost of being wrong is somebody's running build, so the default is inverted:
if the heartbeat directory cannot be read, nothing is a candidate.
